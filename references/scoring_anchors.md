### 1.2 关键口径约束（硬规则）

| 编号 | 规则 | 依据 |
|---|---|---|
| **R1-1** | `状态` 类列**内容仲裁**：枚举含 `通过/驳回/返工/不合格/验收` → 归 quality 喂 E；含 `已完成/进行中/未开始/已关闭` → 归 progress，**不参与打分** | 国内工分表"状态"85% 是进度，不是质量。当质量证据会让所有已完成任务质量分相同，E 维退化为常数，无区分度也无公信力 |
| **R1-2** | `优先级 P0-P3` **只喂 G 紧迫性，绝不喂 D 风险** | 优先级回答"多急"，风险回答"错了多严重"。P0 的紧急文案改动可能零风险，P3 的账务逻辑改动可能高风险。混喂会让紧迫性被算两遍，而真正的风险数据一列都没用上 |
| **R1-3** | **F 永不进小计**，即使有花名册/技能矩阵 | 职级→门槛的映射会让高级别员工的所有任务都获得同样高分，且**同一任务换个人做就变分**，是对特定人群的系统性加成；工分导向分配，此偏差事后极难发现与接受 |
| **R1-4** | 覆盖率按 **"非空且非 0"** 算，`0/空/-/无/暂无/待定/NULL` 一律不算有效 | 大量表用 0 或空格占位，按"非空"算会把 0 当成有效值，导致覆盖率虚高 |
| **R1-5** | 缺失维度 **不填 0、不填默认档、不填中位 3**，一律走降权重重分配 | 填 0 等于惩罚"没记录"；填默认值是凭空造数据，制造虚假一致性 |
| **R1-6** | 难度判据**正交化**：`耗时/金额/出错后果` 类词不得作为难度判据，必须从匹配文本中剥离（排除词表见 3.3） | 防止"困难"与"工时/经济/风险"重复计分——高难度任务本就耗时长，两头都拿高分等于同一件事算两遍 |

## 2. 动态权重规则

### 2.1 算法（确定性，可复现）

```
输入：启用维度集 S（F/I/K 永不入集）
1. 取 S 中各维度的基础权重 w_i
2. 归一化：w_i' = w_i / Σ_{j∈S} w_j
3. 单维上限 40% 封顶（仅当 |S| ≥ 3 时执行）：
     迭代水填充：把超出 40% 的部分，按当前权重比例分配给未触顶的维度，
     直至无维度 > 40% 或全部触顶
4. 输出最终权重 W_i，写入「配置回执」与 caliber_freeze 快照
```

**基础权重池**：A20 / B20 / C20 / D15 / E15 / G10 / H5 / J5（原始和 110；打分时归一到 100%）

> **覆盖度分母 = 100**（`coverage_full_pool = 100`），分子 = `min(启用维度基础权重和, 100)`，全开时 clamp 至 100%。
> 依据：110 是「F/I/K 永久关闭后未重新归一」的历史遗留值，用它做分母会让用户永远凑不满，绝大多数真实批次都会掉进降级分支，反而使分支 A 失去意义。

### 2.2 三个硬性判定

| 判定 | 规则 | 依据 |
|---|---|---|
| **`|S|` ≤ 2 时上限不可满足** | 2 个维度下 2×40%=80% < 100%，无法既封顶又归一。**此时不封顶，强制转降级分支（分支 C）：只出排序，【不出工分单价】** | 诚实优于伪装：2 个维度本就不足以支撑分配，与其造一个违反上限的权重，不如明说体系退化。**工分单价是分配场景的核心输出，维度不足时输出它等于给出一个不可靠的分钱依据** |
| **归一化后权重 < 5%** | **保留，不并入**其他维度，仅配置回执标注「该维度权重 <5%，对结果影响微弱」 | 并入会让权重来源不可追溯，用户无法理解"为什么这次工时权重是 38% 而不是 33%"。保留牺牲简洁、换来可解释——发钱场景下后者更重要 |
| **C 关闭后不设特殊转移** | 一律走通用归一化，不使用 `MONEY_CLOSE_TRANSFER` 之类的特例 | 归一化已自动完成权重再分配；叠加特例会双重分配，导致权重和异常 |

### 2.3 三个算例

**算例① 只启用 B + G**

```
基础：B 20, G 10 → 和 30
归一化：B = 66.67%,  G = 33.33%
封顶：|S| = 2 < 3 → 上限不可满足，不封顶
最终权重：B 66.7% / G 33.3%
覆盖度：30 / 100 = 30%  →  < 45%  →  分支 C（仅描述统计）
判定：⚠️ 单维权重 66.7% 远超上限 + 覆盖度不足 → 强制降级
```

**算例② 启用 A + B + G + D**

```
基础：A20, B20, G10, D15 → 和 65
归一化：A 30.77%, B 30.77%, D 23.08%, G 15.38%
封顶：全部 ≤ 40%，无需调整
最终权重：A 30.8% / B 30.8% / D 23.1% / G 15.4%   （合计 100%）
覆盖度：65 / 100 = 65%  →  ≥ 60%  →  **分支 A（正常，可排名、可用于分配）**
判定：✅ 四个维度均为高可靠维度（工时客观、难度有关键词、紧迫性有截止日、风险有影响范围专列），可支撑分配
```

**算例③ 全开 A + B + C + D + E + G + H + J**

```
基础：20+20+20+15+15+10+5+5 = 110
归一化：A 18.18, B 18.18, C 18.18, D 13.64, E 13.64, G 9.09, H 4.55, J 4.55
封顶：全部 ≤ 40%，无需调整
最终权重：A 18.2 / B 18.2 / C 18.2 / D 13.6 / E 13.6 / G 9.1 / H 4.5 / J 4.5
覆盖度：min(110, 100) / 100 = 100%  →  分支 A（正常，可排名、可用于分配）
判定：✅ 正常；H、J < 5% → 保留但标注「影响微弱」
```

**补充算例④ A + B + G（展示封顶边界）**：`20+20+10=50` → A 40.0% / B 40.0% / G 20.0%，恰好触顶未超限；覆盖度 50% → 分支 B。
**补充算例⑤ B + G + H（展示封顶生效）**：`20+10+5=35` → 归一化 B 57.14% → 封顶压至 40%，溢出 17.14% 按 G:H 比例分配 → **B 40% / G 40% / H 20%**；覆盖度 35% → 分支 C。

### 2.4 与权重联动的自检

| 指标 | 公式 | 判定 | 依据 |
|---|---|---|---|
| **单维集中度** | `max(W_i)` | > 35% → 预警 | 权重集中度是结果方差的主要贡献者；维度关闭后单维被放大，锚点偏差成倍放大 |
| **有效维度数 n_eff** | `(ΣW_i)² / Σ(W_i²)` | `< 3` → 体系退化 | 能同时抓"一维独大"和"两维平分"两种退化，35% 阈值只能抓前者。A40/B40/G20 → 2.78；A50/B50 → 2.00；均匀 6 维 → 6.00 |
| **排序一致性 rank_consistency** | `Spearman(A名次, B名次)`，n ≥ 10 才执行 | `> 0.85` → 实际单自由度 | 直接告诉用户"你设计的多个维度，在这批数据上只相当于 1 个"，比任何提示都有说服力 |

## 3. 维度锚点表（1–5 分，脚本可执行）

**尺度说明**：1–5 五档。依据：人脑稳定分辨上限 7±2；李克特量表跨文化验证；双人一致性（Cohen's kappa）显著高于 10 档；百分制是伪精确（78 与 79 的差异实为噪声）。

> **V4 重大变更**：原 V2/V3 的"模型定性判断""异构双轮打分"机制**全部废除**（用户要求纯脚本执行）。改为**关键词 → 档位映射字典**，脚本可直接 `dict` 查表。原"双轮档差 >1 占比 >20% 判不稳定"的自检，改为「**估算值占比 > 50% 时提示人工抽检**」（见第 8 节 #13）。

### 3.1 B 工时投入（默认启用）

**分档方式：批次内分位数相对分档**（用 `h_eff`，见第 4 节）。依据：不同岗位基准工时不同（设计的"1 天"≠运维的"1 天"），绝对小时数跨岗不可比；分位数天然消除基准差异，且**不需要任何基准工时库**。

| 档 | 分位区间 | 绝对兜底档（n<5 或 P10==P90 时启用） | 示例 |
|---|---|---|---|
| 1 | ≤ P10 | < 4 人时 | 回复一条确认消息 |
| 2 | P10–P30 | 4–16 人时 | 改一版配图 |
| 3 | P30–P70 | 16–40 人时 | 写一篇常规推文 |
| 4 | P70–P90 | 40–80 人时 | 做一份月度数据复盘 |
| 5 | > P90 | > 80 人时 | 从 0 搭一套投放体系 |

- **不量**：审批等待、外部阻塞等被动等待时间（等待不是投入）。无法区分时整体按 0.85 折算并标注精度下降。
- **跨岗混排**：分位数按岗位分组计算，否则系统性低估短周期岗位。
- **触发绝对档时**：报告必须显示「工时基准 = X 小时/人天」，此时换算系数真的影响结果。

### 3.2 G 紧迫性（默认启用）

| 档 | 锚点 | 脚本判定 |
|---|---|---|
| 1 | 无明确 deadline | 截止日为空且无优先级 |
| 2 | 宽松（剩余 > 2 周） | `截止日 − 今日 > 14 天` |
| 3 | 正常（剩余 1–2 周） | `7 天 < 剩余 ≤ 14 天` |
| 4 | 紧（剩余 < 1 周，或有延期风险） | `0 < 剩余 ≤ 7 天` |
| 5 | 救火（≤ 2 天 / 已违约 / 加急 / P0） | `剩余 ≤ 2 天` 或 `已逾期` 或 `加急标记=是` 或 `优先级=P0` |

- **降级**：无可采字段 → 关闭，权重回池。
- **n_eff < 3 时权重上限压到 10%**：多数表截止日统一填月末，信息量极低，在二维体系里给 20% 等于让噪声决定 1/5 的排序。

### 3.3 A 困难程度（**默认启用**）—— **关键词映射表**

> **性质：估算值（estimated=true）**，非实测。报告必须单列，并在**总分旁边**标注。

**为什么默认启用而不是"检测到才启用"**：困难程度是用户点名要求的三个维度之一，不能因为表里没有"难度"列就让它消失。任务名必然存在，所以输入源几乎总能取到——关闭它的唯一理由应当是本批确实推断不出难度，而非缺一个列。

**匹配源**：任务名 + 任务类型 + 标签 + 描述 + 备注（拼接后统一匹配）。
**匹配前处理**：先剔除**排除词**（见下表），再做关键词匹配。

| 档 | 触发关键词（拼接文本中任一命中即触发） |
|---|---|
| **1** | 填写、录入、整理、归档、周报、日报、抄送、转发、按模板、套用、搬运、复制 |
| **2** | 调整、修改、替换、更新、换版、配置、参数、校对、排版、微调 |
| **3** | 撰写、编写、常规、梳理、汇总、对接、跟进、执行、维护、巡检、统计 |
| **4** | 设计、规划、调研、优化、重构、搭建、方案、策略、跨部门、改造、升级、选型 |
| **5** | 从0、从零、原创、探索、预研、攻关、无先例、首次、体系、平台搭建、自研、突破 |

**排除词表（正交化，命中即剔除，不得作为难度判据）**：

| 归属维度 | 排除词 |
|---|---|
| B 工时 | 耗时、用时、工期、加班、连轴、通宵、长期 |
| C 经济 | 金额、合同额、营收、收益、GMV、成本、预算、报价、节约 |
| D 风险 | 故障、事故、投诉、违规、合规、法律风险、不可逆、重大、涉密 |
| G 紧迫 | 紧急、加急、截止、deadline、ddl、立刻、马上 |

**依据**：难度问"这件事多复杂"，不问"多久/多少钱/错了多严重/多急"。不剥离这些词，A 会与 B/C/D/G 重复计分。

**执行规则**：

| 规则 | 内容 | 依据 |
|---|---|---|
| **⓪ 最长匹配优先（先于取最低档执行）** | 命中词存在子串包含关系时，**只保留最长的那个**，再进入取最低档。例：「平台搭建」同时命中档 4 的 `搭建` 与档 5 的 `平台搭建` → 只保留 `平台搭建`（档 5），最终判 **5 档** | 否则「平台搭建」「体系搭建」这类本应判 5 档的任务会被子串 `搭建` 拖到 4 档，与字典设计意图相反。**此规则修正了「取最低档」与「字典含子串词」的冲突** |
| **① 命中多档取最低档** | 一条任务同时命中 2 档与 4 档 → **判 2 档** | 保守原则：低估可通过申诉修正，高估一旦发出去收不回 |
| **标估算值** | 命中结果一律 `estimated=true`，报告单列「估算值，建议人工复核」，**并在总分旁边标注** | 关键词推断不是实测，用户有权知道哪些分是估的；A 退化后可能占 40% 权重，只在方法说明里写会造成信息不对称——这是分配争议的主要来源 |
| **整批命中率 < 20% → 关闭维度** | 本批命中关键词的任务数 / 总任务数 < 20% → **A 维整批关闭**，走降权重重分配，**不填默认档**；提示「任务命名中无难度线索，建议补充难度列或类型列」 | 填默认值等于凭空造数据；用 20% 而非"零命中"是因为个别任务偶然命中不足以支撑整个维度 |
| **不阻断** | 以上全部只标注、不中断流程；提供人工覆写入口 | 唯一允许阻断的是第 9 节失败三件套 |
| **表内有真实难度列时改口径** | 若表里存在真实难度/复杂度等级列，则**优先取列值**，判为客观输入（`estimated=false`），不再走关键词推断 | 对着一列客观等级说"这是定性估算"，用户会觉得工具不懂自己在干什么 |

> 注：A 默认启用后不再有 `enable_ai_difficulty` 开关（用户已明确"不需要模型再判断一次"）。对应开关为 **`enable_keyword_difficulty`（默认 True）**，关闭后 A 维整批不启用。

### 3.4 C 经济效益（检测到才启用）

**量**：可归因直接收益 = 增收 + 成本节约 + 避免损失（财务"贡献毛利"口径）。
**不量**：战略价值、品牌价值、组织能力建设（本版无对应维度）。

| 档 | 锚点（批次内分位） |
|---|---|
| 1 | 无直接经济收益 / ≤ P10（行政、内部事务类） |
| 2 | P10 – P30 |
| 3 | P30 – P70 |
| 4 | P70 – P90 |
| 5 | > P90 **且**有可验证收益凭证（合同/回款/成本对比） |

- **口径统一**：同批次内必须统一为 `合同额/营收/节约/预估价值` 之一，**混用则 C 维无效并关闭**。
- **覆盖率 < 50% → 整批关闭**，走通用归一化。依据：少数任务有金额、多数没有，会造成"有数据的任务系统性高分"，这比缺数据更严重。
- **关闭后必提示**：A/B 权重被放大，结果对其锚点敏感度成倍上升，须先校准。

### 3.5 D 风险责任（检测到才启用）

**量**：出错的代价与不可逆性。**不量**"多急"（那是 G）。

| 档 | 锚点（脚本按专列取值） |
|---|---|
| 1 | 影响范围=个人/本任务，可回滚；或 `涉及客户数=0` 且 `不可逆=否` |
| 2 | 影响范围=本任务，内部返工可修复，修复成本 < 1 人日 |
| 3 | 影响范围=他人任务/部门内流程；或涉及对外承诺；修复 1–5 人日 |
| 4 | 影响范围=跨部门/外部客户；或 `是否关键=是`；或修复 > 5 人日 / 部分不可逆 |
| 5 | 影响范围=全公司/公众；或 `不可逆=是`；或涉合规/安全/法律/品牌危机 |

**为什么必须有 D**：难度低但责任极大的任务（合规申报、故障处置、资金核对）在"难度×工时"下系统性得低分，但组织实际极为依赖。不补 D，工分会驱使人人都去做高难度低责任的探索性任务。

### 3.6 E 质量结果（检测到才启用）—— **计数优先**

| 档 | 锚点 |
|---|---|
| 1 | `返工次数 ≥ 2` 或 `驳回次数 ≥ 2`，或客户评价含 `不满/不合格/退回` |
| 2 | `返工次数 = 1` 或 `驳回次数 = 1`，或评价含 `轻微缺陷/基本合格` |
| 3 | `返工次数 = 0 且 驳回次数 = 0`，或验收结论 ∈ `通过/合格/已完成验收` |
| 4 | 一次通过 且 评价含 `超出要求/好评/满意` |
| 5 | 一次通过 且 评价含 `标杆/可复用/书面表扬/优秀` |

**优先级（严格按序）**：
1. **`返工次数/驳回次数`（客观计数）** —— 有计数就用计数，最可靠
2. **`验收结论` 枚举** —— `通过/合格` → 3 档；`驳回/不合格` → 1 档
3. **`客户评价` 文本** —— 关键词匹配，**必须标 `estimated=true` 并单列**

**依据**：计数是客观记录，评价文本是主观描述。E 是本体系**唯一的防磨洋工对冲项**，其可靠性直接决定工分能否用于分配。

### 3.7 H 协同成本（检测到才启用）

| 档 | 锚点（需协调的外部方数量，按 `协作方/参与人` 列的顿号/逗号/分号计数） |
|---|---|
| 1 | 0（独立可完成） |
| 2 | 1 |
| 3 | 2 |
| 4 | 3–4 |
| 5 | ≥ 5 或跨 ≥ 3 个部门 |

### 3.8 J 复用价值（检测到才启用）—— **三档枚举匹配，禁止连续打分**

| 档 | 枚举类别 | 交付物列关键词（任一命中） |
|---|---|---|
| **1** | **一次性产出**（无人可用） | 稿件、成片、单篇、一次性、交付稿、临时、定稿、终稿 |
| **3** | **可复用组件** | 模板、组件、脚本、工具、插件、素材库、封装、SDK、表单、看板、表格、自动化 |
| **5** | **可复用方法论** | 方法论、SOP、流程规范、标准、手册、白皮书、体系、指南、培训材料、知识库 |

- **三档映射至 1/3/5**：保持 1–5 量表一致，中间档留空（2/4 不使用）。`[需校准]`
- **零命中 → 维度关闭**，走降权重重分配。
- **禁止连续打分**：J 只有三档枚举，不得插值、不得按"复用程度"给 2 或 4 分。
- 依据：三档枚举是脚本能稳定判定的粒度；更细的划分需要语义理解，在纯脚本环境下做不到且不可复核。

## 4. 工时偏离度上限（裁定 1 落地）

### 4.1 公式（用户选定，不得更改形式）

```
h_eff = min(h, P90) + α × max(0, h − P90)          # α = 0.3
```

| 条件 | 处理 |
|---|---|
| **n ≥ 10** | 启用，`h_eff` 参与分位数分档 |
| **n < 10** | **不打折**，`h_eff = h`，报告标注「样本量不足，未启用偏离度上限」 |
| **α** | 默认 **0.3**，`[需校准]`，可配置 |

### 4.2 ⚠️ 效应说明（实现时必读，否则功能静默失效）

`h_eff = min(h,P90) + 0.3×max(0,h−P90)` 是 h 的**严格单调递增变换**（h≤P90 时 h_eff=h；h>P90 时 h_eff=P90+0.3(h−P90)，严格递增）。

**单调变换不改变秩次** → 若拿 `h_eff` 去算分位数分档，其 P10/P30/P70/P90 的**落点成员与用原始 h 完全一致** → **分档结果零变化，打折静默失效**（不报错，是最难发现的失效方式）。

### 唯一正确实现（主理人裁定，不存在第二种写法）

```
1. 分档：用【原始工时 h】计算分位数 → score_B ∈ {1..5}      # 不要用 h_eff 分档
2. K_偏离 = h_eff / h          # ≤ 1；h ≤ P90 时 = 1
   物理可行豁免：有起止日期 且 h ≤ 自然日×8×0.7×1.5 → K_偏离 = 1
   样本豁免：n < 10 → K_偏离 = 1，标注「样本不足，未执行偏离度打折」
3. 单任务工分：P = S × 20 × K_偏离 × K_体量 × K_子任务       # 打折落在总分系数上
                                                          # K_角色 已永久关闭，不存在
```

报告固定句：`该任务工时超出批次 P90 部分按 30% 计入，工分 ×{K}`；被打折任务须单列且 `evidence` 非空。

**为什么是"打总分"而不是"打权重"（削 B 维度权重、其余维度回补）——该方案已被否决**：
- 只剩 B+G 两个维度时，削掉 B 的权重会让 G（紧迫性）被动放大到主导位置——一个虚报工时的任务反而因"很急"拿高分，**与防虚报的意图相悖**；
- 打总分与既有公式结构一致（`S×20×K_体量×K_角色`），一句话可解释，用户看得懂；
- 削权重会让权重随每批数据浮动，破坏配置回执的"可追溯"——用户无法理解"为什么这次工时权重是 22% 而不是 20%"。

**为什么不改写申报值**：原始工时 `h` 全程保留、始终在报告中展示；`K_偏离` 是**计分规则**（口径的一部分，写进配置回执，可复核），不改数据、只按规则计分——不触碰红线 6（禁止静默改分）。

> **不存在** `hours_deviation_weight_compression` 开关。实现方式唯一，即上述三条。

### 4.3 矛盾标记规则（替代 winsorize，不自动改分）

```
若 起止日期可校验 且 h > 可用工时 × 1.5：
    标记 hours_conflict = True
    → 报告单列「工时矛盾」清单，供人工复核
    → 【不自动改分】
可用工时 = (结束日 − 开始日 + 1) × hours_per_manday × workday_factor
```

**为何否决无条件 winsorize（>P95 一律按 P95 计）**：
1. 一条真实的 200 小时系统迁移会被系统性低估——虚报的是少数，被削的是最辛苦的那批人，这个代价在发钱场景下会被立刻感知，且比虚报更难解释（"我做了最大的项目反而被削平"）；
2. 不经人工确认就改写申报值，属于**算法黑箱改分**，触碰红线。

**依据**：「大」不等于「假」。仅以"物理不可行"作为虚假的客观证据，其余情况只做温和折扣（α=0.3 保留 30% 而非归零）。

### 4.4 起止日期交叉校验的四档可用性

| 数据条件 | 能做什么 | 标志 |
|---|---|---|
| 开始日 + 结束日都在 | 完整交叉校验（可用工时 = 自然日 × 8 × 0.7，含首尾） | `strong` |
| 只有结束日 + 有创建/下发日 | 以下发日当开始日，可用工时 × 0.8（不确定下发即启动） | `weak`（标 `estimated`） |
| 只有结束日 | 做不了单任务校验。改批次级：同月度内工时之和 > 该月总人时 × 1.5 → 提示 | `batch` |
| 都没有 | 不做。报告明写「无日期锚点，工时无法交叉验证，虚报风险不可控」 | `none` |

**依据**：校验能力必须如实告知，否则用户会以为"有防护"而实际没有——这比没防护更危险。

## 5. 单任务小计与总分算法

### 5.1 单任务小计

```
S = Σ(score_i × W_i) / Σ(W_i)                  # 缺失维度从分子分母同时剔除
```
- `score_i ∈ [1,5]`，`S ∈ [1,5]`
- 工时偏离度打折**不进入小计**，只在 §5.2 的 `K_偏离` 上作用于单任务工分（见 4.2，主理人裁定）
- 缺失维度**不填 0、不填默认档、不填中位 3**，从分子分母中同时剔除（权重自动回补其他维度）
- **依据**：填 0 惩罚"没记录"（数据缺失通常与任务性质无关）；填默认值是凭空造数据，会让缺数据的任务虚假趋同

### 5.2 单任务工分

```
P = S × 20 × K_偏离 × K_体量 × K_子任务
```
- `× 20` → 工分落在 **20–100**，符合百分直觉
- **`K_偏离`**：工时偏离度打折系数，`= h_eff/h ≤ 1`，含物理可行豁免（见 4.2）
- `K_体量` **默认关闭**（`K_体量 = 1.0`）；如需启用：`1 + 0.1 × log₂(h / 批次中位h)`，封顶 1.3、保底 0.8
- `K_子任务`：见 5.3，默认 1.0（仅在有层级列时才可能 <1）

### 5.3 子任务折算 —— 可加性自检（非硬编码）

| 条件 | 处理 |
|---|---|
| `|父工时 − Σ子工时| / 父工时 < 10%` | 父是**容器**，**不计分**，只汇总子任务 |
| `父工时 > 1.1 × Σ子工时` | 父是**独立任务**，**不折价**（K=1.0） |
| 其他 | `K_子任务 = 0.6`（可配置） |

**依据**：无条件对父任务 ×0.6 会对"父本身就是独立大任务"的情况双重折价。

### 5.4 总分（方案 A，锁定）

```
T = Σ P_j        # 仅对 L1 + L2（完整度 ≥ 60%）求和；L3（< 60%）不计入总分、不参与排名
```
- **不使用方案 B（按工时加权）**：`P` 已是"单位任务价值密度"，再按工时加权等于工时被计两次（一次在 B 维度，一次在汇总权重），违反去耦原则；且 A 的结果可直接对接分配池，B 不可。
- **工分单价 = 分配池 ÷ T**

### 5.5 完整度分层与层内排名

```
完整度 = 该任务已启用维度中「有值」的权重和 / **本批启用维度权重和** × 100%
```

**分母是"本批启用维度权重和"，不是理论满池 100**。依据：分层问的是"这个任务相对**本批次能拿到的满分**有多全"。若用 100 作分母，当本批只启用 75 权重时，一个字段齐全的任务永远只有 75%，永远进不了 L1——分层机制直接失效。
「整批维度够不够」由**批次级覆盖度分支**（第 6 节）负责，两套机制分工明确，不可混用。

> 另输出 `completeness_vs_100`（以 100 为分母）作为跨批次对照，仅展示、不参与分层判定。

**分层为两刀（90 / 60）**，不用三刀：

| 层 | 区间 | 处置 |
|---|---|---|
| **L1 高置信** | ≥ 90% | 层内可排名、可计入总分 |
| **L2 中置信** | [60%, 90%) | 层内可排名、可计入总分；整批标注「含中置信任务」 |
| **L3 低置信** | < 60% | **不计入总分、不参与排名**，单独列清单供人工复核 |

**为什么取消 75 这一刀**：分层阈值是固定值，而权重粒度是浮动的（本批启用哪些维度不确定），两者组合会出现**空区间**。实测：某批启用权重和为 **75**（A20+B20+C20+G10+H5）时，完整度只能取 100% / 73.3% / 53.3%——缺一个 20 权重的维度即降到 73.3%，缺两个降到 53.3%，中间没有别的值。此时 `[75%,90%)` 落空、`[60%,75%)` 只装得下 73.3% 这一种，分层实际退化成"缺一个维度就掉档"。两刀（90 / 60）在任何启用集下都无空区间：73.3% 稳落 L2，不再被一刀切出局。

**为什么必须分层**：`S = Σ(score×W)/ΣW` 数学正确，但有副作用——**缺失越多，分数方差越大**（单维算分完全由那一维决定，多维算分被拉向中值）。直接按 S 排序会**系统性惩罚数据完整的任务、奖励数据稀少的任务**。

**排名规则**：`rank_within_layer = True`。**报告必须明写「跨层名次不可直接比较」**。

> ⚠️ 完整度（任务级）与第 6 节覆盖度（批次级）是两个不同概念，不可混淆。

## 6. 覆盖度三档（裁定 2）与报告固定句

### 6.1 定义与判定

```
覆盖度 = min( Σ(启用维度的基础权重), 100 ) / 100 × 100%
```
> **分母固定为 100**（`coverage_full_pool = 100`），分子为启用维度基础权重之和，上限 clamp 至 100%。
> 依据：原始权重池和 = 110 是「F/I/K 永久关闭后未重新归一」的历史遗留值；用它做分母会让用户永远凑不满，绝大多数真实批次都掉进降级分支，反而使分支 A 失去意义。
> 例：A+B+G+D = 20+20+15+10 = 65 → 覆盖度 65% → **分支 A**（可分配）。

| 分支 | 区间 | 输出 |
|---|---|---|
| **A** | **≥ 60%** | 正常：可排名、**可用于分配** |
| **B** | **45% – 60%** | 可排名，**不建议直接分配**；提示"补充 X 列可将覆盖度提升至约 Y%" |
| **C** | **< 45%** | **仅输出描述统计，不出可比工分** |

**为何弃用 <50% 一刀切**：恰好等于 50% 时归属不明；且 45–60% 区间有真实中间价值（能排序、不能分钱），一刀切浪费了这部分信息。

### 6.2 报告固定句（逐字使用）

**分支 A**：
> 本批覆盖度 XX%（≥60%），维度覆盖充分，工分可用于价值分配。使用前仍须经团队共识与人工复核。

**分支 B**：
> ⚠️ 本批覆盖度 XX%（45%–60%），**可排名但建议不要直接用于分配**。补充「X」列可将覆盖度提升至约 Y%。当前建议：先用作工作量排序参考，补齐数据后重跑再分配。

**分支 C**：
> ⚠️ 本批覆盖度仅 XX%（<45%），维度覆盖不足，**本结果仅为描述性统计，不构成可比工分，不能作为分配依据**。建议补充以下列后重跑：XXX。

**分支 D（附加判定，与 A/B/C 并列展示）**：
> ⚠️ 体系退化预警：有效维度数 n_eff = X.XX（< 3）[，且难度与工时排序一致性 ρ = X.XX（> 0.85），实际只有 1 个有效自由度]。本批工分仅作排序参考，**不建议用于分配**。

### 6.3 补充列提升预估（分支 B/C 必输出）

脚本按"未启用维度的基础权重"倒序，输出建议补充的列：

| 未启用维度 | 建议补充列 | 可提升覆盖度 |
|---|---|---|
| C 经济效益 | 金额/合同额/节约额 | +18.2pp |
| D 风险责任 | 影响范围/是否关键/SLA | +13.6pp |
| E 质量结果 | 返工次数/驳回次数/验收结论 | +13.6pp |
| A 困难程度 | 难度等级/复杂度 | +18.2pp |
| G 紧迫性 | 截止日期 | +9.1pp |
| H 协同成本 | 协作方/参与人 | +4.5pp |

### 8.1 疑似拆分检测（批内 4 条，首次即可运行）

任一条命中即**提示，不判定不扣分**：

1. 任务名去序号/期次/括号后做前缀聚类，同簇 ≥ 3 条且合计工时占全批 ≥ 30%
2. 工时 ∈ {8, 16, 24, 40}h 的占比 > 70% 且中位 < 8h（按整天凑数特征）
3. 任务名平均长度 < 6 字且任务数 > 30（颗粒度过细）
4. **高难度档（4–5）中工时低于全批 P30 的比例 > 50%**（既难又极短，逻辑矛盾）

首次运行将分布快照与 `caliber_freeze` 写入 `baseline.json`，**下次运行自动启用环比**（报告注明「环比检测已存档，下次生效」）。
**依据**：原"任务数环比 +50% 且平均工时 −30%"在首次运行 100% 无法执行。

### 8.2 单位混用判定（裁定 3：列名 > 日期锚点反算 > 数量级）

```python
# 优先级 1：列名单位（最可靠，直接读）
if 列名含 "小时" / "h" / "hours" / "工时":        → 该列按小时，不换算
elif 列名含 "天" / "人天" / "人日" / "工作日":     → 该列按人天，× hours_per_manday
elif 存在 "计划工时" 与 "实际工时" 两个独立列:     → 逐列各自换算，不判混用

# 优先级 2：日期锚点反算（客观外部证据）
elif 存在起止日期:
    for t in sample(tasks_with_dates, k=3):
        pred_h = 工期自然日 * hours_per_manday * workday_factor
        if abs(t.raw / pred_h - 1) < 0.4:       → 该批按小时
        elif abs(t.raw * 8 / pred_h - 1) < 0.4: → 该批按人天

# 优先级 3：数量级推断（兜底，仅提示不强制）
else:
    if 中位值 > 24:  → 疑似小时
    elif 中位值 <= 10: → 疑似人天
    else:            → 无法判定，按默认 8 小时/人天 并标注
```

**为何弃用"同时存在 >24 与 ≤10 的值即判混用"**：纯人天表里 0.5 与 30 人天并存是常态，该判据假阳性率过高。
**依据**：有外部锚点（列名/日期）就不靠分布猜。日期是独立录入字段，用它反算工时量纲是唯一客观判法。

## 11. 红线声明（供 SKILL.md 与报告引用）

1. **工分是任务分，不是个人绩效等级。** 禁止输出"某人应得 X 分 / 应评为 X 级"这类确定性结论。若需按人汇总，输出的是"该人负责任务的工分合计"，并必须标注：**此为任务工分合计，不等同于个人绩效结论，用于分配前须经团队共识与人工复核。**

2. **禁止任何淘汰/扣罚名单规则。** 本体系不产出、也不得推导"应淘汰/应扣罚人员名单"。

3. **每条规则必须有依据。** 无依据的主观规则不得进入本文件；所有经验参数必须标注 `[需校准]`。

4. **依赖推断的维度必须标「估算值」并单列。** A 难度（关键词推断）、E 质量（评价文本推断）判为 `estimated=true`，报告单列「估算值，建议人工复核」。**不得用估算值冒充实测值。**

5. **不得含对特定人群的系统性偏差。** F 技能门槛永久关闭正是因此——职级→门槛的映射会让高级别员工的所有任务都获得加成，而工分导向分配，此偏差事后极难被发现与接受。

6. **不得用算法黑箱改分。** 所有自检项**只提示、不自动改分**——工时矛盾、疑似拆分、分布偏斜、偏离度打折，均输出提示与清单，最终判断权归人工。**原始申报数据全程保留、始终展示，永不改写。**

7. **不得在数据不足时伪装成可用。** 覆盖度 < 45%、`n_eff < 3`、或 `|S| ≤ 2` 时，必须输出第 7.3 节降级声明，明确「不能作为分配依据」，不得输出看似可用于发钱的完整结果。

8. **不得阻断流程（失败三件套除外）。** 所有数据问题一律"标注 + 人工覆写入口 + 继续出报告"，仅第 9 节三种情形允许失败退出。
